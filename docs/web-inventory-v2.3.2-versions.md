# WebInventory v2.3.2 — version capture

Decision record and implementation notes for v2.3.2. Constraints carried forward: stock Windows PowerShell 5.1 + .NET
Framework 4.7.2 (also PS7), no installs, inventory only (no exploitation, no brute force, no default credentials, no
directory enumeration), no loss of accuracy, standalone tool.

## Problem
After v2.3.1, 1,327 product names carried an NVD CPE but 729 of them came only from rules that capture no version
(a title, a cookie, a favicon). `-StoreQuery Vulnerabilities` can then match only `all-versions` entries and KEV CVEs
for them. More CPEs cannot help; the version has to be read from somewhere.

## Decision
Add **version-only rules**: a rule output marked `"vo": true` that reads a version from a response the scanner
already receives and adds it to a product another rule detected. No new request is sent for a version, and no new
detection can appear.

- Engine (`Matcher.Evaluate` / `Matcher.Aggregate` / `Matcher.Merge`):
  - a version-only output is created with confidence 0 and no implies/excludes/requires/gate;
  - it joins a detection through the existing merge passes (same kind and CPE product, then same kind and name), and
    an implied product joins it the same way;
  - when a detection rule joins, the detection rule's identity is kept (name, category, confidence, CPE product,
    gate) and only the version is taken;
  - version precedence when a version-only output takes part: captured by a detection rule > captured by a
    version-only rule > written into a rule (`"v":"1.5.0+"` on a favicon). Without version-only outputs nothing
    changes (the longer version wins, as before);
  - what no detection rule joined is dropped before excludes/requires are evaluated;
  - `nameInfo` (used by implies) ignores version-only outputs.
  - rule option `b` (`"o": "b"`): the pattern is matched against the base64 decoding of the value (UTF-8; a value
    that is not base64 is skipped; such rules have no literal prefilter). n8n's only version is inside the base64 JSON
    of its `n8n:config:sentry` meta tag.
- Rules: `src/version-rules.json`, generated by `tools/version/gen_rules.py` from the reviewed entries in
  `tools/version/rules.py`, appended to the built-in pack by `build.py` (`v:` ids). One output per CPE product the
  product's detection rules use. Each rule has an `ex`/`exv` example; `-SelfTest` fails on a built-in or `v:`
  example mismatch.

## Acceptance rules
See `tools/version/README.md`: the value is the release version as NVD numbers it; it has the parts the releases
have (no major-only or major.minor of three-part releases); it is in GET /, its same-host redirects, the 404 probe,
robots.txt, security.txt, the favicon or an `-IdentifyPaths` response; pre-releases are not matched; library versions
only from CDN paths, never query strings. Evidence classes: container (the product's own image, two releases),
source (the template or code that prints it), published sample (WhatWeb passive plugins, nuclei-templates detection
templates, Recog examples, webappanalyzer).

## Tooling
- `vlab.py` runs a product image (Docker) and records exactly what a default scan fetches; `grep` lists where the
  image's version string occurs. `replay.ps1` feeds the recording into the real matcher (the built script's engine
  and packs) and prints detections with versions.
- `wplab.py` installs WordPress plugins at known versions and reports, per asset under the plugin's folder, whether
  `?ver=` equals the plugin version or the WordPress version (which WordPress appends when a plugin passes none).
- `targets.py`, `coverage.py`, `external.py`: what is still missing, and which public databases have a candidate.

  from the product's templates or code, 37 from published samples, 6 WordPress plugins from the plugin lab,
  20 JavaScript libraries from CDN paths and library file names).

  the 637 without, 31 share their CPE with a product whose rules read one; the others, by reason: no-known-location
  390, hidden 87, not-version 42, hardware 30, other-url 27, platform 21, coarse 7, unverified 2. Per product:
  [`web-inventory-v2.3.2-coverage.md`](web-inventory-v2.3.2-coverage.md).

  Metabase 5, WordPress plugins 5, Checkmk 4, Mattermost 3). Details in `dist/README.md`.

## Behaviour changes to flag
- Scan output: products that were reported without a version now carry one (`Products`, `CPEs`, JSONL detections),
  and a favicon-implied version such as Roundcube `1.5.0+` is replaced by the real one when a version-only rule finds
  it. No product appears or disappears.
- Store: the first run after the upgrade records `changed` events for services whose `Products`/`CPEs` gain a version
  (both are material fields). The change log names the fields.
- Vulnerabilities: services that were matched `product-only`/`all-versions` are now matched by version, so rows move
  from KEV-only listing to `version`/`range` and the row count changes.

## Not covered, and why
